=== mote reliability: recovery evidence ===

Curated results from three runs: the systemd restart policy on a workstation,
and the startup gate plus per-node respawn on the real robot (auldbot,
Raspberry Pi 5, aarch64, 2026-07-26). See README.md in this directory.

--- 5. the installed systemd units (auldbot, after install + reboot) ---------

Two defects surfaced the moment the units were installed for real and the robot
rebooted; both are fixed, and the evidence below is from after the fix.

  (a) install.sh hardcoded WorkingDirectory=@HOME@/Mote, so units installed from
      the worktree pointed at ~/Mote — a checkout on main with no `self-check`
      task. ExecStartPre exited 127 and bringup looped 69+ times. The gate did
      behave correctly throughout: ExecMainStatus=0, i.e. ExecStart never ran
      and the robot stayed idle. Fixed with @REPO@, derived by install.sh from
      its own location.

  (b) mote-health/mote-record declared Wants=mote-bringup.service. While they
      were themselves looping, each cycle fired a start request for bringup, and
      a requested start BYPASSES RestartSec:

        1785069721.238107  mote-health:  Scheduled restart job, counter at 1.
        1785069721.238835  mote-bringup: Scheduled restart job immediately on
                                         client request, counter at 67.

      0.7 ms apart. bringup hammered every ~3.5 s while its own
      RestartUSecNext already read 30s — the backoff was fully defeated. Fixed
      by dropping Wants= (After= for ordering, own WantedBy= for boot start).

Gate + startup, real hardware under systemd:
  [PASS] servo_ping: id=7 OK (pos=3927); id=9 OK (pos=3767); all 2 responded
  [PASS] lidar, camera, disk_space, clock, robot_yaml, active_site
  self-check: READY
  Started mote-bringup.service.
  mote-bringup + mote-health: active/running, NRestarts=0, /health = OK

Service-level recovery — SIGKILL the unit's MainPID:
  NRestarts 0 -> 1; the gate re-ran on the way back up (servo_ping PASS,
  self-check: READY), Started mote-bringup.service, /health back to OK.

Watchdog, live rather than merely configured:
  WatchdogUSec=15s, WatchdogTimestamp advancing, NotifyAccess=all,
  StatusText="health monitor up" — sd_notify READY/status/watchdog all land.

The RestartSec ramp, measured (transient unit that always fails). Run 1 above
only ever measured the first restart; this is the whole curve:
  NRestarts=0  next=2s
  NRestarts=1  next=3.437543s      actual gaps: 2, 4, 6, 10, 18, 30, 30 s
  NRestarts=2  next=5.908353s
  NRestarts=3  next=10.155112s     geometric, ratio (30/2)^(1/5) ~ 1.72
  NRestarts=4  next=17.454322s
  NRestarts=5  next=30s            ceiling reached at step 5
  NRestarts=6  next=30s            and held
  Exactly RestartSec=2 + RestartSteps=5 + RestartMaxDelaySec=30.


--- 6. one-command start, services disabled (auldbot) -----------------------

The units are installed but not enabled, so a session is started by hand. This
checks that the health monitor comes with the mission rather than only with
systemd — `pixi run robot` and nothing else:

  health_monitor:            running, pid started by the launch itself
  /health:                   OK
  publishers on /health:     1          (no duplicate monitor)
  /diagnostics_agg:          mote OK; scan, scan_filtered, joint_states, camera,
                             odometry, localization all ok
  pixi run self-check:       still works standalone -> READY

`localization` reads ok rather than informational-absent because the nav mission
runs AMCL, which supplies map->odom. On the bare base it reports absent without
degrading the robot, which is the reason that severity exists.
